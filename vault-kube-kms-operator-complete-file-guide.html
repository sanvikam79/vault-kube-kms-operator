1. Core Go Source

cmd/main.go HC

The operator entry point. Starts the controller-runtime manager, registers the kmsv1alpha1 scheme so Kubernetes knows about VaultKMSConfig objects, and wires up the VaultKMSConfigReconciler. Also configures health probes, metrics, leader election, and webhook TLS. This file runs when the operator pod starts inside the OCP cluster.

internal/controller/vaultkmsconfig_controller.go JT

The reconcile loop — the heart of the operator. When the admin creates or updates a VaultKMSConfig CR, Kubernetes fires a watch event. This file handles it:

Reconcile() is called
  1. Fetch the VaultKMSConfig CR by name
  2. Build desired status:
       KMSPluginImage: version.PluginImage   ← digest-pinned, baked at compile time
  3. If current status != desired → write status back to CR
  4. Red Hat's keyController reads this status → injects sidecar into kube-apiserver

Logic is HashiCorp's. The field name (kmsPluginImage) is jointly agreed with Red Hat because their code reads it.

internal/version/version.go HC

A single variable:

var PluginImage = "docker.io/hashicorp/vault-kube-kms:0.1.0-beta"

In local dev this default is used. In release builds the CRT pipeline overrides it at compile time via -ldflags "-X ...version.PluginImage=registry...@sha256:...". This is the only place the plugin image digest is set — no YAML, no ConfigMap, no env var. The baked-in digest flows into VaultKMSConfig.status.kmsPluginImage at runtime.

2. CRD API Types

api/v1alpha1/vaultkmsconfig_types.go JT

Defines the Go structs for the VaultKMSConfig CRD. Two sections:

SectionWho owns the fieldsContents
VaultKMSConfigSpecHC HashiCorpvaultAddress, vaultKeyPath, vaultNamespace, authentication (AppRole), TLS — all Vault-specific fields only HashiCorp knows
VaultKMSConfigStatusRH Red Hat named itkmsPluginImage — the field Red Hat's keyController reads. Red Hat defined the field name; HashiCorp writes the value.

Also contains CEL validation rules on all spec fields (URL format, path format, DNS name rules etc).

api/v1alpha1/groupversion_info.go RH

Registers the API group kms.openshift.io/v1alpha1 with the Kubernetes scheme. The group name uses Red Hat's openshift.io domain — Red Hat owns this. HashiCorp cannot change the group name unilaterally because Red Hat's keyController is hardcoded to look for this type.

api/v1alpha1/zz_generated.deepcopy.go GEN

Auto-generated by controller-gen via make generate. Contains DeepCopy() methods required by controller-runtime for all API types. Never edit manually — regenerated on every make generate run.

3. Tests

internal/controller/vaultkmsconfig_controller_test.go HC

Unit tests for the reconciler using envtest (real etcd + kube-apiserver, no cluster needed). Three test cases:

TestWhat it verifies
should populate the status with the plugin imageWhen a CR is created with required fields, operator writes version.PluginImage into status
should set the plugin image regardless of optional spec fieldsOptional fields (TLS, vaultNamespace) do not affect image injection
should preserve the plugin image after spec changesWhen admin updates vaultAddress/vaultKeyPath, image digest stays the same (not re-encrypted)

internal/controller/suite_test.go HC

Ginkgo test suite bootstrap. Starts envtest (downloads etcd + kube-apiserver via setup-envtest), loads the VaultKMSConfig CRD from config/crd/bases/, registers the scheme, starts the reconciler. Both setup-envtest (binaries) and CRDDirectoryPaths (schema) are required for tests to work.

test/e2e/e2e_test.go + e2e_suite_test.go HC

End-to-end tests run against a real Kind cluster with OLM installed. Creates a real VaultKMSConfig CR, verifies the operator pod reconciles it correctly (status gets the plugin image), tests operator upgrade flow. Runs via make test-e2e — takes 5-10 minutes.

4. Build & Release

Dockerfile HC

Three-stage build following the VSO pattern required for Red Hat certification:

Stage 1 (builder):    golang:1.26 — compiles the operator binary
                      ARG LD_FLAGS — receives digest from CRT pipeline
                      go build -ldflags "$LD_FLAGS" → bakes PluginImage into binary

Stage 2 (build-ubi):  ubi-minimal — only used to refresh CA certificates
                      microdnf upgrade ca-certificates

Stage 3 (release-ubi): ubi-micro — final minimal image
                       Copies binary + CA bundle + LICENSE
                       OCI labels required by Red Hat preflight certification

5. CRD and Config (Generated)

config/crd/bases/kms.openshift.io_vaultkmsconfigs.yaml GEN

The actual CRD schema YAML. Generated by controller-gen from the Go struct annotations in vaultkmsconfig_types.go. When the OLM operator is installed, this CRD is applied to the cluster — this is what registers VaultKMSConfig as a valid Kubernetes type. Contains all CEL validation rules.

config/rbac/role.yaml GEN

Generated RBAC ClusterRole. Gives the operator permission to get/list/watch/create/update/patch VaultKMSConfig objects and their status subresource. Without this the operator pod cannot read or write CRs.

config/manager/manager.yaml HC

The operator Deployment manifest. Defines the operator pod — image, resource limits, health probe ports, security context (non-root). This is what OLM deploys into the cluster when the admin installs the operator.

config/manifests/bases/vault-kube-kms-operator.clusterserviceversion.yaml HC

The hand-authored CSV base. Contains operator metadata shown in OperatorHub: displayName, description, maturity (stable), installModes (AllNamespaces), owned CRDs list. This is the template — make bundle combines it with generated RBAC and deployment spec to produce the full bundle CSV.

6. OLM Bundle (Generated by make bundle)

bundle/manifests/vault-kube-kms-operator.clusterserviceversion.yaml GEN

The complete OLM ClusterServiceVersion. Generated from the bases CSV + kustomize + hack scripts. Contains: full deployment spec, RBAC permissions, owned CRDs, containerImage annotation, spec.replaces for upgrade graph, com.redhat.openshift.versions annotation. This is what OLM reads to install and manage the operator.

bundle/manifests/kms.openshift.io_vaultkmsconfigs.yaml GEN

Copy of the CRD YAML included in the bundle so OLM can register the CRD when installing the operator.

bundle/metadata/annotations.yaml GEN

OLM bundle metadata. Channel (stable), package name (vault-kube-kms-operator), minimum OpenShift version (v4.18 — set by hack script). Red Hat's certification pipeline reads these annotations.

7. Hack Scripts

hack/set_csv_replaces.sh HC

Sets spec.replaces: vault-kube-kms-operator.vX.Y.Z in the bundle CSV. This builds the OLM upgrade graph — tells OLM that this version upgrades from the previous one. Uses the previous git tag automatically. Skipped gracefully on first release (no previous tag).

hack/set_openshift_minimum_version.sh HC

Appends com.redhat.openshift.versions: v4.18 to bundle annotations. Red Hat's certification pipeline reads this to ensure the operator is only installable on OCP 4.18+. Value 4.18 is the first OCP release expected to ship the cluster-kube-apiserver-operator changes that read VaultKMSConfig.status.

hack/set_containerImage.sh HC

Sets the containerImage annotation in the bundle CSV to match the actual operator image in the deployment spec. OperatorHub displays this in the UI. Uses yq to read the image from the deployment spec and write it back as an annotation.

hack/install_copywrite.sh HC

Downloads the HashiCorp copywrite tool. Used by make bundle to add BUSL-1.1 copyright headers to all generated files (YAML, Go, shell scripts).

hack/kind-config.yaml HC

Kind cluster config for e2e tests. Pins the node image to kindest/node:v1.33.1 and configures the local registry mirror (localhost:5001) so the operator image can be pulled by the Kind cluster during e2e tests.

hack/boilerplate.go.txt HC

BUSL-1.1 copyright header template. Used by controller-gen (make generate) to prepend the correct license header to all generated Go files.

10. Project Metadata

PROJECT HC

kubebuilder project config. Records the project name (vault-kube-kms-operator), module path, domain (openshift.io), and registered API resources. operator-sdk generate kustomize manifests reads this to determine the CSV filename. Wrong project name = duplicate CSV error.

go.mod HC

Go module definition. Module path: github.com/hashicorp/vault-kube-kms-operator. All import paths in the codebase resolve relative to this. Also pins controller-runtime, client-go, and k8s.io versions which must stay in sync.

.copywrite.hcl HC

HashiCorp copywrite tool config. Sets license to BUSL-1.1, copyright year 2025, and excludes .idea/ and build/ from header checks.

LICENSE HC

BUSL-1.1 (Business Source License). This is why the operator code cannot be open sourced or included in the OCP release payload — it is HashiCorp proprietary. The entire OLM operator design exists because of this license restriction.

CODEOWNERS HC

GitHub CODEOWNERS file. Defines which HashiCorp team must review PRs. Ensures the right team is notified on all changes.

11. How the New OLM Design Works End-to-End

STEP 1 — HashiCorp releases operator
  CRT pipeline builds operator binary with:
    -ldflags "-X ...version.PluginImage=registry...vault-kube-kms@sha256:abc123"
  Publishes operator bundle to Red Hat Operator Catalog

STEP 2 — OCP admin installs operator
  kubectl apply -f subscription.yaml
  OLM reads bundle → applies CRD to cluster → starts operator pod
  Operator pod starts, registers Watch on VaultKMSConfig objects

STEP 3 — Admin creates VaultKMSConfig CR (one time)
  kubectl apply -f vault-kms-config.yaml
    spec:
      vaultAddress: https://vault.company.com:8200
      vaultKeyPath: transit/keys/ocp-key
      authentication:
        type: AppRole
        appRole:
          secret:
            name: vault-approle-creds

STEP 4 — Operator reconciles (automatic)
  Watch fires → Reconcile() called
  Reads: spec.vaultAddress, spec.vaultKeyPath (admin's Vault config)
  Writes: status.kmsPluginImage = version.PluginImage (baked digest)
  Result in etcd:
    status:
      kmsPluginImage: registry.connect.redhat.com/hashicorp/vault-kube-kms@sha256:abc123

STEP 5 — Admin points APIServer at the CR
  kubectl edit apiserver cluster
    spec.encryption.kms.pluginConfig:
      kind: VaultKMSConfig
      name: my-vault-kms

STEP 6 — Red Hat keyController acts (automatic)
  Reads VaultKMSConfig.status.kmsPluginImage
  Reads VaultKMSConfig.spec fields (vaultAddress, vaultKeyPath, auth)
  Builds vault-kube-kms sidecar container with correct CLI flags
  Injects sidecar into kube-apiserver static pod
  kube-apiserver starts encrypting etcd with Vault Transit keys
